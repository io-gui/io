# @io-gui/three

## Defaults

- Import from `@io-gui/three` (pulls peer `three` / webgpu).
- New apps: one **`Editor`** (the host: playing state, selection, tools, operators) showing a **`Document`** (the content); mount views with **`threeViewport({ editor, view })`**. Switch content with `editor.document = doc`: every viewport, the selection and each view's navigation follow.
- **Put content in a `Document` subclass**, self-contained so it opens in any editor: scene in the constructor, GPU setup (compute, PMREM) in `onRendererInitialized(renderer)`, animation in `onAnimate(delta, time)`, per-frame GPU work (compute steps, `CubeCamera.update`, renders into targets) in `onBeforeDraw(renderer, delta)`, the camera it is presented through as `activeCamera` (it need not be in the scene; views set with `setCameraView()` follow it), controls as `@Property`s with groups registered next to the class. Don't touch the editor, views or DOM from a document.
- **Animate from the document's `timeline`** (`currentTime`, `duration`, `frameRate`, `loop`, `autoplay`). `onAnimate(delta, time)` runs on every change of `timeline.currentTime`: playback, scrubbing, stepping. Derive state from `time` where you can (it then scrubs and loops); advance mixers and other integrators by `delta` (negative going back). Game-like content driven by interaction (crossfades on button presses) can't follow `time`: use the timeline as a clock, `if (delta > 0) mixer.update(delta)`, and leave pause and step to the editor's transport. Set defaults with `super({timeline: new Timeline({autoplay: true, duration: 20}), ...args})`. Shader animation uses `this.timeline.timeNode`, not TSL's global `time`. `autoplay` is a hint: whoever opens the document sets `editor.isPlaying = doc.timeline.autoplay`.
- Playback UI: `threeTimeline({ editor })` (transport buttons with `three:` icons, scrubbable range, time fields; follows `editor.document`). `threeTimelineRange({ timeline })` is the range alone.
- Scene tree UI: `threeScenegraph({ editor, disclosure })`: rows with type icons, everything expanded, the selection highlighted; click selects like a viewport click, and a new active object from anywhere is revealed (ancestors expanded, row scrolled into view). Double-click or F2 renames through the built-in `object.rename` operator (`{id, name}`). Bind `disclosure` to `Storage({key, storage: 'local', value: {}})` to keep collapsed objects by uuid. Type icons come from `getObjectIcon(object)`; give your own classes one with `registerObjectIcon(MyClass, 'app:icon')` (subclasses inherit it).
- **Register editor configs next to your class** (`registerEditorConfig` / `registerEditorGroups` right after its definition), on the narrowest class; never on `Object` or another broad base. `Document` shows only tone mapping in Main and sends everything else to Advanced, so list your document's controls in `Main` (explicit names beat that regex).
- **Edit the document through transactions** (`document.transact(tx => tx.copy(obj, 'position', v))`; `tx.set` assigns and throws on read-only properties such as `position`, `copy` copies into the held object), or operators (`editor.operators.run(id, props)`), not by writing Three.js objects directly: that is what keeps undo, redraw and future sync working. Interactive edits are modal operators (`invoke` returns `'running'`, `modal` gets events, Escape rolls back).
- **Selection** is `editor.selection` (per document): change it with `selection.set(uuids)` / `selection.edit()...commit()`, read `getObjects()` / `getActiveObject()`, bind UI to `selection.version` / `selection.active` / `selection.activeObject` (the active Object3D, e.g. for an inspector). Picking goes through a `Picker` (`defaultPicker`, async). Set `userData.selectable = false` on helpers (grids, gizmo meshes) so they cannot be picked.
- Tools are `ToolDefinition`s on `editor.tools`, activated per view kind + mode (`editor.setActiveTool('3d', 'object', id)`); `view.profile` (`full | select | navigate | none`) filters what a viewport installs. Built in: the Move tool `transform.translate` (gizmo + modal operator of the same id).
- **Never add helpers (grids, outlines, handles, `CameraHelper`, light helpers, `SkeletonHelper`) to `document.scene`.** Cameras, lights, skeletons and clipping groups already get helpers from the built-in helper overlays (`cameraHelpers`, `lightHelpers`, `skeletonHelpers`, `clippingHelpers`). Draw anything else as overlays (`overlayTypes.register`, `view.setOverlay(id, on)`; declare a new id in `ViewOverlays` with `declare module '@io-gui/three'`) or gizmo groups (`ToolDefinition.createGizmoGroups`). Different rendering per view = a registered `ViewPipeline` named by `view.pipeline` (e.g. a `PostProcessingPipeline`), not renderer tweaks in `onAnimate`.
- UV view: `new View({kind: 'uv', profile: 'select'})` shows the selected meshes' UV layouts.
- **Components** (edit mode, `editor.operators.run('object.editmode_toggle')` / Tab; `mesh.select_mode` / 1 2 3): stored as `ComponentSet` bitsets in `editor.selection` (`edit().components(uuid, domain, size)`, `getComponents(uuid, domain)`). Get sizes and indices from `getTopology(geometry, 'mesh')` or `getGeometryAdapter(object)`; `point` is a welded position, not a buffer vertex. The UV view stores `corner` selection unless `selection.uvSync`.
- Prefer package math editors (`ThreeVector3`, …) for Three math types in inspectors.

## Gotchas

- **Importing the package registers editor configs** for Three.js classes (side-effect). Expected.
- **WebGPU only.** Default **shared `WebGPURenderer`** across viewports; each viewport has its own **CanvasTarget**. Tone mapping, clear color and render target are set per draw by the viewport's compositor: set `document.toneMapping` or `view.toneMapping`, not `renderer.toneMapping`. Bloom works the same way: `document.bloom` (`Bloom`: `enabled`, `strength`, `radius`, `threshold`) is the document's look, `view.bloom` (`true`, `false` or `null` to follow the document) decides per view. `view.msaa` multisamples the content (needed for `alphaToCoverage`); a `PostProcessingPipeline` created with `{msaa: false}` (TRAA) ignores it.
- Pipelines output **linear** color; the viewport tone-maps when presenting. A `PostProcessingPipeline` keeps `outputColorTransform = false`; don't add `renderOutput()` to its graph.
- **Only `renderScheduler` renders.** Viewports are tagged dirty and drawn next frame. After editing the scene outside `onAnimate`, call `editor.requestRender()` (or `editor.notify({kind})`) or nothing redraws. Never call render methods on viewports. Adding objects outside transactions (async model loads) needs `notify({kind: 'structure'})`, or the scene graph does not list them.
- UI that follows a document without drawing it (lists, outliners) registers `renderScheduler.addListener({document, onDocumentChanges})` and gets each frame's drained changes. Never drain a document yourself (`drainChanges()` belongs to the scheduler) or poll the scene.
- Renderer init is **async** — do GPU setup in `onRendererInitialized(renderer)`. A document's runs once per renderer, before that renderer first draws it, also when the document is opened later. `onBeforeDraw(renderer, delta)` runs once per frame and renderer before its views draw the document's changes; `delta` counts only time played forward, so simulations never rewind.
- `isPlaying: false` on the editor ⇒ the timeline does not advance and the editor's `onAnimate` does not run; a document's `onAnimate` still runs when its timeline is scrubbed, stepped or set. Non-visible viewport ⇒ no draw.
- `timeline.frameRate` does not change playback (continuous, paced by the display); it sets frame stepping, scrub snapping and divider steps.
- Size belongs to each viewport (`viewport.width/height`); the editor has no resize hook. Scene cameras are fitted to the viewport aspect at draw time.
- **View state lives on `View`**, not the viewport or the document. A view holds intent (axis view, first or named scene camera) that carries across documents, and remembers its resolved navigation per document: `viewport.view.navigation` (target, rotation, distance, axis view, scene camera by uuid), `overscan`, `clearColor`. Pass a `view` to keep navigation across remounts. Choose the camera on the view: `new View().setAxisView('top')` (`'free'` = default perspective; also leaves a scene camera), or `.setCameraView()` to look through the first scene camera (falls back to the `free` view until one is in the scene; looked for again in each document switched to). With several scene cameras use `.setCameraView('name:<name>')` or `'uuid:<uuid>'`; an id without a prefix warns and uses the `free` view. Use `viewport.getViewCamera()` for picking; never mutate scene cameras to fit a viewport. After editing `view.navigation` directly, call `view.markNavigationChanged()`. Camera moves are not reactive mutations (they run per pointer move); follow them with the view's `navigation-changed` event.
- Component indices are valid for one topology: after changing a geometry's positions or index, old sets are ignored (size mismatch). Component picking uses the rest shape (no skinning / morphs) and triangles (quad diagonals are edges).
- **Viewports are not core `IoGl`.** IoGl is 2D shader quads (sliders, colors, `ThreeTimelineRange`); viewports are full Three WebGPU.
- **All viewport input goes through `viewport.inputRouter`** (priority capture). Never add pointer/wheel listeners to a viewport directly, and never use `OrbitControls` on it: navigation is `NavigationBehavior` + a `Keymap` (`navigationKeymaps.default | blender | maya`, or pass `keymap`).
- Pointer tools are `ToolDefinition.createBehaviors(ctx)` behaviors at tool priority; use `ctx.host.getViewCamera()` for rays. Return false from `wantsCapture` for input that navigation should get.
